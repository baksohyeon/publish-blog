# 13. Advanced Page Tables  
페이징 방식은 페이지 테이블의 크기로 인해 메모리 공간을 많이 차지하는 점이 문제 중 하나로, 페이지 테이블 자체도 크지만 프로세스별 페이지 테이블이라는 구조상의 문제로 더욱 큰 메모리를 필요로 한다. 이에 대한 해결 방법으로 ‘페이지 크기를 키우는 방법’과 ‘멀티 레벨 페이징’ 등이 있다.  
  
  
# 더 큰 페이지 할당  
  
페이지 크기를 늘려 페이지 수를 줄이는 방식으로 페이지 테이블의 크기를 줄이고자 하는 방법.  
  
## 시스템의 지원  
  
MIPS, SPARC, x86-64 (AMD64), ARM 등의 많은 아키텍처가 페이지 크기를 다양하게 지원하므로, 필요 시 더 큰 페이지를 할당받도록 구성할 수 있다.  
  
일반적으로 4KB, 8KB 등의 작은 페이지 크기를 사용하지만, 프로그램에 따라 필요 시 4MB와 같은 큰 크기의 페이지를 사용할 수 있으며 데이터베이스 관리 시스템(DBMS)이나 고성능 프로그램에서 많이 사용된다.  
  
  
📌 아래 단점에도 불구하고 위 언급한 프로그램에서는 주로 TLB 미스를 줄이기 위해 큰 페이지 크기를 사용한다.  
  
  
## 운영체제의 지원  
  
다양한 크기의 페이지를 지원하는 시스템에서 운영체제가 다양한 크기의 페이지를 프로그램마다 사용할 수 있도록 대응하려면 가상 메모리 관리 모듈이 매우 복잡해진다. 비교적 간단한 사용 방법으로는 추가 인터페이스를 정의하여 프로그램이 대형 페이지를 직접 요청할 수 있도록 할 수 있다.  
  
이러한 대형 페이지 지원을 Linux에서는 Huge pages, BSD에서는 Super Pages, Windows에서는 Large pages라고 부르며 Linux에서는 대형 페이지로 사용할 크기와 페이지의 수를 설정하여 사용한다.  
  
  
```  
hugepagesz=1G  
hugepages=10  
```  
  
  
위와 같이 설정 시 1GB 크기의 대형 페이지 10개를 사전에 할당(총 10GB)하여 사용한다. 단, *기본적으로는* 2MB와 1GB만 [지원](https://aws.amazon.com/ko/premiumsupport/knowledge-center/configure-hugepages-ec2-linux-instance/)하며, 총 메모리 용량보다는 작게 설정하여야 한다. 참고로 기본 페이지 크기는 4KB이다.  
  
Debian Wiki에 따르면 대형 페이지 테이블을 따로 두고 관리하지만, 이에 대한 표준(테이블의 위치 등)은 없는 것으로 보인다. 또한, 위의 내용과 달리 플래그 설정 및 아키텍처에 따라 다른 크기의 페이지를 사용할 수도 있는 것으로 보인다.  
  
참고 페이지: [Hugepages - Debian Wiki](https://wiki.debian.org/Hugepages#Multiple_huge_page_size_support)  
  
  
## 프로그램의 지원  
  
위의 Linux 시스템에서의 지원 사례와 같이 다양한 크기의 페이지를 지원하는 시스템에서 프로그램은 별도로 요청하여 대형 페이지를 사용할 수 있도록 되어 있으므로 관련하여 프로그램이 대형 페이지를 지원하도록 설계되어야 한다. MySQL, PostgreSQL과 같은 DBMS에는 이와 관련된 설정이 있다.  
  
  
## 단점  
  
### 내부 단편화 (Internal Fragmentation)  
  
외부 단편화는 잘게 쪼개서 남은 잉여 공간을 사용할 방도가 없어서 발생한다면, 내부 단편화는 큼직하게 공간을 나눠 두는 바람에 실제 사용량 대비 할당받은 공간이 남아 이 공간에 대한 낭비로 인해 발생한다.  
  
# 하이브리드  
  
페이징과 세그멘테이션을 결합하여 페이지 테이블의 크기를 줄이는 방법. 프로그램별 페이지 대신 논리 세그멘트별(*코드, 힙, 스택*) 페이지 테이블 구성으로 변경하고자 한다.  
  
## 하이브리드 방식에서의 세그멘테이션  
  
- 베이스 레지스터 — 세그멘트 시작 주소 → **페이지 테이블의 시작 주소**  
- 바운드 레지스터 — 세그멘트의 크기 혹은 끝 → **페이지 테이블의 끝 = 최대 유효 페이지 개수**  
- 가상 주소의 구조  
  
  
![Pasted image 20230320121637.png](./attachments/Pasted%20image%2020230320121637.png)  
  
  
세그멘테이션에서 2비트로 구성 시 코드, 힙, 스택 외에 사용하지 않는 구분이 하나 남았던 것과 달리, 남는 구분을 ‘미사용’으로 분류하게 된다. → 할당되지 않은 페이지는 각 세그멘트별 페이지 테이블에서 공간을 차지하지 않는다.  
  
  
## 단점  
  
1. 세그멘테이션의 단점을 그대로 가져온다.  
    1. 특정 사용 패턴을 가정하므로 유연하지 못함  
    2. 드문드문 사용되는 힙과 같은 경우 여전히 페이지 테이블을 낭비  
2. 페이지 테이블 크기에 제한이 없고 다양한 크기를 가지므로, 테이블용 공간을 확보하기 어렵다. → **외부 단편화를 유발**한다.  
  
  
# 멀티 레벨 페이지 테이블  
  
선형 페이지 테이블을 트리 구조로 표현하여 사용하지 않는 주소 공간은 최대한 할당도 하지 않도록 하는 방법.  
  
## 기본 개념  
  
페이지 테이블을 페이지 크기의 단위로 나눠, 테이블 내 페이지 전체가 유효하지 않으면 해당 페이지를 할당하지 않는다.  
  
### 페이지 디렉토리 (Page Directory)  
  
페이지 테이블의 할당 여부와 위치를 파악한다. 이러한 구성요소를 페이지 디렉토리 항목(PDE, Page Directory Entries)이라고 한다.  
  
- 할당 여부 (유효 비트, Valid bit)  
- 위치 정보 (페이지 프레임 번호, Page Frame Number)  
  
  
![Pasted image 20230320121715.png](./attachments/Pasted%20image%2020230320121715.png)  
  
위 페이지 디렉토리 사진에서 201과 204 외에는 유효하지 않았으므로 201과 204만 페이지 테이블이 구성되며, 나머지는 할당되지 않았다.  
  
  
## 장단점  
  
### 장점  
  
- 사용된 주소 공간 크기에 비례하여 페이지 테이블 공간이 할당 → 작은 크기의 페이지 테이블로 주소 공간 표현  
- 페이지 크기로 분할하여 관리가 용이 → 테이블 할당 혹은 확장 시 빈 페이지를 가져다 쓰기만 하면 된다.  
  
### 단점  
  
- TLB 미스 시 주소 변환을 위해 두 번의 메모리 로드가 발생하므로 비용이 상대적으로 비싸다.  
- 선형 페이지 테이블보다 탐색이 복잡.  
  
### 비교  
  
| -                     | 멀티 레벨 페이지 테이블        | 선형 페이지 테이블             |  
| --------------------- | ------------------------------ | ------------------------------ |  
| 메모리 할당           | 빈 페이지만 찾아 사용하는 원활 | 연속적인 물리 메모리 공간 필요 |  
| TLB 미스 시 주소 변환 | PD, PTE 접근으로 최소 2번      | 한 번의 접근                   |  
  
## 2단계 이상의 사용  
  
페이지 디렉토리가 너무 큰 경우에는 그만큼의 연속된 물리 메모리 공간이 필요하므로 선형 페이지 테이블과 달리 페이지 단위로 테이블을 나눈 의미가 사라진다.  
  
따라서 페이지 디렉터리 자체를 멀티 페이지로 나눠 트리의 단계를 늘린다.

## TLB의 사용  
  
TLB를 검사하여,  
  
- 히트 시 — 테이블 참조 없이 물리 주소 직접 구성  
- 미스 시 — 테이블의 모든 단계를 거쳐 물리 주소 구성  
  
  
  
  
## 역 페이지 테이블(inverted page table)  
  
메모리 프레임마다 항목 1개. 프로세스와 증가 없으며 크기 고정.  
  
프로세스가 늘어나도 테이블 수가 그대로라 **효율성 증대**  
  
최악의 경우 페이지 테이블을 전체 탐색해야 하므로 **성능 하락 →** 성능 향상을 위해 주소 해시 테이블 사용  
  
PowerPC가 이 구조를 사용.  
  
### 구조  
  
- 논리 주소  
    - 프로세스 ID  
    - 페이지 번호  
    - 오프셋  
- 물리 주소  
    - 메모리 프레임 번호  
    - 오프셋  
- 페이지 테이블  
    - 프로세스 ID  
    - 페이지 번호  
      
    인덱스가 곧 메모리 프레임 번호  
  
  
  
## 페이지 테이블을 메모리 이외의 공간에 비치하기  
  
- 커널 가상 메모리  
- 디스크로 스왑
