# Concept of Paging  
  
- 운영체제가 가상 메모리를 관리하는 방법  
1. **Segment (가변 크기로 분할)**  
:  프로세스의 주소 공간을 여러 개의 가변 길이 논리 세그먼트(예: 코드, 힙, 스택)로 나누는 것  
  
  
![Pasted image 20230312181932.png](../../attachments/Pasted%20image%2020230312181932.png)  
  
1. **Paging (고정된 방법으로 분할)**  
: 프로세스의 주소 공간을 고정된 크기의 단위(페이지)로 나누고, 물리적 메모리도 같은 크기로로 `페이지 프레임(Page frame)` 슬롯으로 나눈다.   
	프로세스 당 Page table을 갖고있고, 가상 메모리 주소를 실제 메모리 주소로 변환하는 과정이 필요하다.  
  
  
  
  
  
  
- **Paging의 장점**  
	1. **Flexibility**: 추상화된 주소 공간을 효과적으로 지원 (heap, stack 성장 방향과 사용 방법에 대해서 신경쓸 필요 없다.)  
	2. **Simplicity**: 가상 주소 공간의 미사용 부분 관리가 더 쉬움  
	3. **Efficiency**: 페이징(설계에 따라)은 메모리를 고정된 크기의 단위로 분할하기 때문에 외부의 단편화 문제를 해결할 수 있다.  
  
  
- **Paging 단점**  
	4. 메모리 낭비 (실제 애플리케이션 데이터가 아닌 페이지 테이블로 메모리가 가득 차게 됨)  
	5. 페이지 테이블에 액세스하기 위한 추가 메모리 액세스 필요하다.

## - Address Translation  
  
### Page Table  
- **페이지 테이블**  
  가상 주소(또는 실제로는 가상 페이지 번호)를 물리적 주소(물리적 프레임 번호)에 매핑하는 데 사용되는 단순한 데이터 구조   
  → 모든 데이터 구조 사용 가능  
    
  
![Pasted image 20230312175944.png](../../attachments/Pasted%20image%2020230312175944.png)  
  - 가장 간단한 형태: **선형 페이지 테이블**이라고 불리는 단순한 <font style="color:#6082B6">배열</font>  
    1. OS는 가상 페이지 번호(VPN)로 배열을 인덱싱  
    2. 이 인덱스를 통해 페이지 테이블 항목(PTE)을 검색  
    3. 필요한 물리적 프레임 번호(PFN)를 찾는다.   
  
  
  
주소 공간의 각 가상 페이지가 물리적 메모리에 배치되는 위치를 기록하기 위해 운영 체제는 일반적으로 페이지 테이블이라는 프로세스 단위의 데이터 구조를 유지한다.  
페이지 테이블의 주요 역할은 주소 공간의 각 가상 페이지의 주소 변환을 저장하여 각 페이지가 물리적 메모리의 어디에 있는지 알 수 있도록 하는 것이다.   
  
  
  
```c  
movl <virtual address>, %eax  
```  
  
가상 주소를 eax 레지스터에 저장하여 변환한다.  
  
  
- **프로세스의 가상 주소를 물리주소로 변환하기 위한 2가지 필수 요소**  
	1. 가상 페이지 번호(VPN) - 주소 상위 2비트  
	: 물리 메모리의 페이지 프레임  
	2.  페이지 내 오프셋  
	: 페이지 프레임에서 어느 바이트에 있는지   
  
<font style="color:indianred">가상 주소</font> <페이지 <font style="color:indianred">VPN</font>, 거리 Offset> → <font style="color:#6082B6">물리 메모리</font> <프레임 <font style="color:#6082B6">PFN</font>, 거리 Offset>  
  
  
  
![Pasted image 20230312171653.png](../../attachments/Pasted%20image%2020230312171653.png)  
이 그림에서 Va5는 가상 주소의 최상위 비트이고, Va0는 최하위 비트이다.   
  
  
프로세스가 가상 주소를 생성하는 경우 OS와 하드웨어를 결합하여 의미 있는 물리적 주소로 변환해야 한다.   
  
---  
  
**예시)** 작은 주소 공간(64바이트)을 가진 프로세스가 가상 주소 21번의 메모리 액세스를 실행하고 있다고 가정해보자.  
  
```c  
movl 21, %eax  
```  
  
프로세스가 생성한 이 가상 주소를 변환하려면 가상 페이지 번호(VPN)와 페이지 내 오프셋의 두 가지 구성 요소로 분할해야 한다.   
  
프로세스의 가상 주소 공간이 64바이트이므로 가상 주소($2^6$ = 64)에 총 6비트가 필요하다.  
  
페이지 크기는 64바이트의 주소 공간에서 16바이트마다이므로 총 4 개의 페이지를 사용할 수 있다.  
4개의 페이지를 구분하기 위해 상위 2비트에 저장하는 것이다.  
페이지 크기는 16바이트이다.  
  
![Pasted image 20230312221110.png](../../attachments/Pasted%20image%2020230312221110.png)  
  
`21`을 바이너리 형식으로 변환하면 `010101`을 얻을 수 있다.  
  
![Pasted image 20230312171745.png](../../attachments/Pasted%20image%2020230312171745.png)  
  
가상 주소 `21`은 가상 페이지 `'01'(또는 '1')`의 `5번째 (0101번째)` 바이트에 있다.   
  
가상 페이지 번호를 사용하여 페이지 테이블을 인덱싱하고 가상 페이지 1이 어떤 물리적 프레임에 있는지 찾을 수 있다.   
  
  
![Pasted image 20230312171956.png](../../attachments/Pasted%20image%2020230312171956.png)  
위의 페이지 테이블에서 물리적 프레임 번호(PFN)(물리적 페이지 번호 또는 PPN이라고도 함)는 7(바이너리 111)이다.   
따라서 VPN을 PFN으로 대체하여 이 가상 주소를 변환하여 물리적 메모리에 로드한다.   
  
  
오프셋은 페이지의 어떤 바이트가 필요한지 알려줄 뿐이므로 오프셋은 변환되지 않는다는 점에 유의해야 한다.   
우리의 최종 물리적 주소는 0111 0101 (10진수로는 117)이며, 정확히 필요한 데이터를 로드하고 가져온다.

### Page Table Entry (PTE, 페이지 테이블에서 각 페이지의 정보)  
  
  
  
- Page Table in Kernel Physical Memory  
![Pasted image 20230312172329.png](../../attachments/Pasted%20image%2020230312172329.png)  
  
페이지 테이블은 단순히 32비트 페이지 지정자의 배열임  
페이지 테이블은 그 자체로 하나의 페이지이므로 4KB의 메모리 또는 최대 1K의 32비트 항목을 포함합니다.  
  
  
![Pasted image 20230312180007.png](../../attachments/Pasted%20image%2020230312180007.png)  
  
메모리 페이지를 주소 지정하는 데는 두 가지 수준의 테이블이 사용된다.  
  
상위 수준에는 `페이지 디렉터리`가 있습니다.   
페이지 디렉터리는 두 번째 레벨의 페이지 테이블을 최대 1K까지 주소 지정합니다.   
  
두 번째 수준의 `페이지 테이블`은 최대 1K 페이지까지 주소 지정한다.   
따라서 하나의 페이지 디렉터리에서 주소 지정하는 모든 테이블은 1M 페이지($2^{20}$)를 주소 지정할 수 있다.  
각 페이지에는 4K 바이트 $2^{12}$ 바이트가 포함되므로 한 페이지 디렉터리의 테이블은 80386의 전체 물리적 주소 공간에 걸쳐 있을 수 있다. ($2^{20} \times 2^{12} = 2^{32}$).  
  
**x86 기준** 현재 페이지 디렉터리의 물리적 주소는 `페이지 디렉터리 기본 레지스터(PDBR)`라고도 하는 CPU 레지스터 <font style="color:#6082B6">CR3</font>에 저장된다.   
  
메모리 관리 소프트웨어에는 모든 작업에 하나의 페이지 디렉터리를 사용하거나 각 작업에 하나의 페이지 디렉터리를 사용하거나 이 두 가지를 조합하여 사용할 수 있는 옵션이 있다.  
  
  
각 프로그램 인스턴스를 실행하기 전에 올바른 페이지 테이블에 대한 포인터와 함께 이 레지스터를 로드하는 것이 운영 체제의 작업이다.  
  
각 메모리 액세스 시 CPU는 레지스터에서 테이블 포인터를 읽고 테이블에서 액세스한 페이지에 대한 매핑된 프레임을 찾는다.   
이 작업은 전적으로 하드웨어에서 이루어지며 실행 중인 프로그램에는 전혀 보이지 않습니다.   
  
또한 번역 프로세스의 속도를 높이기 위해 많은 CPU 아키텍처에는 마지막 변환 결과를 기억하는 특수 캐시가 있다.  
  
  
  
  
  
### Common Flags of Page Table Entry  
  
VPN으로 해당 프로세스의 page table 배열을 인덱싱하고 변환을 위해 해당 인덱스의 page table entry(PTE)를 조회한다.   
 여기서 PTE는 page table에서 각 page의 정보라고 생각하면 된다.  
  
  
- **Example: X86 Page Table Entry**  
![Pasted image 20230312173424.png](../../attachments/Pasted%20image%2020230312173424.png)  
  
페이지 프레임 번호(PFN) 외 비트 정보  
  
- `Present(P) 비트`  
: 이 페이지가 물리적 메모리 내에 있는지 아니면 디스크에 있는지(즉, 스왑아웃되었는지)를 나타낸다.   
	이 비트는 물리적 메모리보다 큰 주소 공간을 지원하기 위해 주소 공간의 일부를 디스크로 스왑하는 방법을 알아볼 때 필요하다.  
	(스왑은 거의 사용되지 않는 페이지를 디스크로 이동하여 OS가 물리적 메모리를 확보할 수 있도록 함)  
  
- `Read/Write 비트(R/W)`: 이 페이지의 쓰기 허용 여부를 결정  
  
- `User/Supervisor 비트(U/S)`: User mode 프로세스가 페이지에 접근할 수 있는지에 대한 비트  
  
- `PWT, PCD, PAT, G 비트`: 이 페이지의 하드웨어 캐싱이 어떻게 작동하는지 결정  
  
- `Accessed 비트(A, Reference Bit)`: 최근 참조된 적이 있는지에 대한 정보 (페이지 교체 정책에서 사용됨)  
: 페이지가 액세스되었는지 여부를 추적하는 데 사용된다.  
	어떤 페이지가 자주 액세스되고 필요하며 메모리에 보관해야 하는지를 결정하는 데 유용하다. (페이지를 교체할 때 중요하다.)  
  
- `Dirty 비트`: 페이지가 메모리에 저장된 후 변경되었는지 여부를 나타낸다.  
  
- `Valid 비트`  
: 일반적으로 특정 변환이 유효한지 여부를 나타내는 데 사용된다.  
	예를 들어, 프로그램 실행이 시작되면 코드와 힙, 주소 공간의 한쪽 끝에 스택이 있고 다른 쪽 끝에 스택이 있다.  
	그 사이의 미사용 공간은 모두 유효하지 않은 것으로 표시되며, 프로세스가 이러한 메모리에 액세스하려고 하면 OS가 트랩을 생성하여 프로세스가 종료될 수 있다.   
	따라서 유효 비트는 할당되지 않은 주소 공간을 지원하기 위해 중요하다.   
	단순히 주소 공간에서 사용하지 않는 페이지를 모두 비활성화하면 해당 페이지에 물리적 프레임을 할당할 필요가 없으므로 메모리를 크게 절약할 수 있다.  
  
  
- `Protection 비트`  
: 페이지의 읽기, 쓰기, 실행이 가능한지 여부를 나타낸다.  
	이 비트에 의해 허용되지 않는 방식으로 페이지에 액세스하면 OS가 트랩을 생성한다.  
  
  
  
  
- **추가 지식**  
x86_64 아키텍처는 4레벨 페이지 테이블과 4KB의 페이지 크기를 사용한다.   
각 페이지 테이블은 레벨에 관계없이 512개 항목으로 고정된 크기를 갖는다.   
각 항목의 크기는 8바이트이므로 각 테이블의 크기는 512 * 8B = 4KB이므로 한 페이지에 정확히 들어 맞음.  
  
각 레벨의 페이지 테이블 인덱스는 가상 주소에서 직접 파생된다  
  
![Pasted image 20230312182742.png](../../attachments/Pasted%20image%2020230312182742.png)  
  
각 테이블 인덱스는 9비트로 구성되어 있으며, 이는 각 테이블에 2^9 = 512개의 항목이 있음.  
가장 낮은 12비트는 4KB 페이지의 오프셋입니다(2^12바이트 = 4KB).   
48비트에서 64비트는 버려지므로 x86_64는 48비트 주소만 지원하므로 실제 64비트가 아니다.  
  
48~64비트는 버려지지만 임의의 값으로 설정할 수는 없습니다.   
대신 이 범위의 모든 비트는 주소를 고유하게 유지하고 5단계 페이지 테이블과 같은 향후 확장을 허용하기 위해 비트 47의 복사본이어야 한다.   
이를 부호 확장이라고 부르는데, 이는 2의 보수에서 부호 확장과 매우 유사하기 때문입니다. 주소가 올바르게 부호 확장되지 않으면 CPU는 예외를 던진다.

# Problems  
## Problem 1: 페이징 테이블 저장 문제  
  
예를 들어 4KB page를 갖는 32 비트의 가상 주소 공간을 생각해보겠습니다. 이 가상 주소는 20비트의 VPN, 12비트의 offset으로 분할됩니다. VPN이 20개의 비트로 표현된다라는 말은 OS가 각 프로세스에 대해 관리해야 하는 page수가 100만 개 정도 된다는 것입니다. 또한 하나의 page의 정보를 저장하기 위한 page table의 크기가 4바이트라고 한다면 4바이트 * 100만 = 4MB입니다. 이러한 프로세스가 100개라면... 400MB의 메모리를 필요로 하게 됩니다. 이를 CPU의 레지스터에 저장한다는 것은 불가능하므로 page table은 메모리에 저장하게 된다고 일단 생각하겠습니다. 실제로는 메모리에 저장되는 것이 아닙니다.  나중에 OS가 사용하는 메모리가 가상화될 수 있다는 것을 알게 되는데요, page table은 OS 가상 메모리에 저장됩니다. 또한 디스크로 swap 될 수도 있습니다.   
  
페이지 테이블 관리의 가장 큰 문제는 페이지 테이블의 크기가 작지 않다는 것이다.  
  
예를 들어, 일반적인 32비트 주소 공간에서 4KB의 페이지가 있다고 가정해보자.   
이 시스템이 가질 수 있는 물리 메모리의 최대 크기는 4GB 이다.  
  
이 가상 주소는 20비트 VPN과 12비트 오프셋으로 분할된다   
(1KB의 페이지 크기 당 10비트가 필요, 4KB는 12비트)  
  
20비트 VPN은 각 프로세스에서 OS가 관리해야 하는 $2^{20}$개 (대략 100만개)의 변환이 있음을 나타낸다.   
실제 변환에 더해 페이지 테이블 항목(PTE) 당 4바이트가 필요하다면 각 페이지 테이블에 필요한 메모리는 4MB가 된다.   
  
100개의 프로세스가 실행되고 있다고 가정한다면, 주소 변환에만 400MB의 메모리가 필요하다.   
  
따라서 페이지 테이블은 CPU 레지스터에 저장하는 것이 아니라, OS가 관리하는 물리적 메모리에 존재한다.  
OS의 메모리 자체를 가상화할 수 있기 때문에 페이지 테이블을 OS의 가상 메모리에 저장할 수 있다. (디스크에 스왑할 수도 있다).   
  
  
## Problem 2: 페이징은 너무 느리다.  
  
1. 원하는 PTE(Page Table Entry)의 위치를 찾으려면 page table의 시작 위치가 필요함   
    1. 만약 큰 메모리 공간에서 작은 페이지를 사용하면(page size가 작으면), page table 크기가 매우 커질 수 있음. 이 경우 원하는 PTE 위치 찾는데 시간이 길어질 수 있다.  
2. 모든 메모리 참조에 대해 페이징을 수행하려면 OS에서 하나의 추가 메모리 참조를 수행해야 함  
    1. 페이징에 대한 오버헤드가 증가할 수 있음. 작은 페이지 크기를 사용할 경우 이런 추가 비용이 더 발생함  
  
  
  
```c  
movl 21, %eax  
```  
  
다시 말하지만, 주소 21에 대한 명시적 참조를 살펴볼 것이므로 명령어 가져오기에 대해 걱정할 필요가 없다.  
  
  
이 예제에서는 하드웨어가 변환을 수행한다고 가정한다.   
필요한 데이터를 가져 오기 위해 시스템은 먼저 가상 주소(21)를 올바른 물리적 주소(117)로 변환해야 한다.   
  
따라서 주소 117에서 데이터를 가져 오기 전에 시스템은 먼저 프로세스의 페이지 테이블에서 적절한 페이지 테이블 항목을 가져와 변환을 수행한 다음 물리적 메모리에서 데이터를 로드해야 한다.  
  
이를 위해 하드웨어는 현재 실행 중인 프로세스에서 페이지 테이블이 어디에 있는지 알아야 한다.  
여기서는 단일 페이지 테이블 베이스 레지스터에 페이지 테이블의 시작 위치의 물리적 주소가 포함되어 있다고 가정한다.   
  
원하는 페이지 테이블 항목(PTE)의 위치를 찾기 위해 하드웨어는 다음과 같은 기능을 수행한다.  
  
이 예에서 VPN Mask는 0x30(16진수 또는 110000)으로 설정되어 전체 가상 주소에서 VPN 비트를 선택하고, SHIFT는 4(오프셋의 비트 수)로 설정되어 있으므로 VPN 비트를 아래로 이동하여 올바른 정수형 가상 페이지 번호를 형성한다.   
  
예를 들어, 가상 주소 21(010101)에서 마스크하면 이 값은 010000이 된다. 이를 이동시키면 01이 된다.   
  
  
이것이 가상 페이지 1이 된다.   
  
그런 다음 이 값을 페이지 테이블 베이스 레지스터가 가리키는 PTE의 배열에 대한 인덱스로 사용한다.  
  
이 물리적 주소를 알면 하드웨어는 메모리에서 PTE를 꺼내어 PFN을 추출하고 가상 주소의 오프셋과 연결하여 필요한 물리적 주소를 형성할 수 있다.  
  
구체적으로는 SHIFT에 의해 왼쪽으로 이동된 PFN을 생각할 수 있다.  
  
그런 다음 오프셋과 OR을 통해 최종 주소를 다음과 같이 구한다.  
  
```c  
// 가상 메모리 주소에서 VPN 추출(VPN_MASK, SHIFT 값 이용)  
VPN = (VirtualAddress & VPN_MASK) >> SHIFT  
  
// PTE 주소 계산. PTBR(Page Table Base Register) 값과 VPN 이용  
PTEAddr = PTBR + (VPN * sizeof(PTE))  
  
// 계산된 PTE 주소로부터 PTE(Page Table Entry)값 읽어옴  
PTE = AccessMemory(PTEAddr)  
  
// PTE의 Valid bit 값을 확인해 유효한지 검사하고 유효하지 않으면 예외 발생  
if (PTE.Valid == False) RaiseExceptoin(SEGMENTATION_FAULT)  
// PTE의 Pretecotion bit 값을 확인해 페이지에 접근할 수 있는지 확인하고   
// 접근 권한이 없으면 PROTECTION_FAULT 예외 발생  
else if (CanAccess(PTE.ProtectBits) == False) RaiseException(PROTECTION_FAULT)  
else  
	// 페이지에 접근할 수 있으면, 물리적 메모리 주소 계산  
	offset = VirtualAddress & OFFSET_MASK  
	// 이 때, PFN(Page Frame Number) 값과 offset 값 사용  
	PhysAddr = (PTE.PFN << PFN_SHIFT) | offset  
	// 계산된 물리적 메모리 주소로부터 데이터를 읽어와 레지스터에 저장함  
	Register = AccessMemory(PhysAddr)  
  
  
```  
  
  
```c  
// 가상 주소에서 vpn만 추출한다  
VPN = (VirtualAddress & VPN_MASK) >> SHIFT  
  
// Page Table 주소에 vpn 값으로 현재 접근하는 프로세스의 PTE 값을 찾는다.  
PTEAddr = PageTableBaseRegister + (VPN * sizeof(PTE))  
  
// 가상 주소에서 offset만 추출한다  
offset = VirtualAddress & OFFSET_MASK  
  
// offset과 PFN 값으로 실제 메모리 주소를 얻는다.  
PhysAddr = (PFN << SHIFT) | offset  
```  
  
이렇게 얻어진 실제 메모리 주소의 데이터를 %eax 레지스터에 넣으면 드디어 메모리에서 값을 가져오는 데 성공하는 것입니다. 어떤가요? 복잡하지 않나요.. 이를 수행하면 메모리에서 데이터를 가지고 오는데 메모리를 한 번 참조하는 것이 아닌 두 번 참조하게 되고 성능도 그만큼 저하되게 됩니다. 즉 성능 저하라는 문제가 발생하게 되죠. Paging 방법을 사용하는 것은 메모리 가상화를 위한 좋은 방법처럼 보이지만 성능도 안 좋고 메모리도 많이 사용하는 방법인 것입니다. 즉 이를 극복해야 실제로 사용할 수 있습니다.  
  
- **Accessing Memory With Paging**  
```c  
 // 가상 주소에서 VPN을 추출한다.  
 VPN = (VirtualAddress & VPN_MASK) >> SHIFT  
  
 // 페이지 테이블 엔트리(PTE)의 주소를 형성한다.  
 PTEAddr = PTBR + (VPN * sizeof(PTE))  
  
 // PTE 가져오기  
 PTE = AccessMemory(PTEAddr)  
  
 // 프로세스가 페이지에 접근할 수 있는지 확인  
 if (PTE.Valid == False)  
	 RaiseException(SEGMENTATION_FAULT)  
 else if (CanAccess(PTE.ProtectBits) == False)  
	 RaiseException(PROTECTION_FAULT)  
 else  
 // Access is OK: 실제 주소를 생성하고 가져온다.  
	 offset = VirtualAddress & OFFSET_MASK  
	 PhysAddr = (PTE.PFN << PFN_SHIFT) | offset  
	 Register = AccessMemory(PhysAddr)  
```  
  
마지막으로, 하드웨어는 메모리에서 필요한 데이터를 꺼내어 eax 레지스터에 넣을 수 있다.   
  
이를 통해서 프로그램은 메모리에서 값을 로드할 수 있다.  
  
요약하면, 각 메모리 참조에서 어떤 일이 일어나는지에 대한 초기 프로토콜을 설명한다.   
  
그림 18.6은 기본적인 접근 방식을 보여줍니다. 모든 메모리 참조(명령어 가져 오기 또는 명시적 로드 또는 저장)에 관계없이 페이징은 먼저 페이지 테이블에서 변환을 가져 오기 위해 하나의 추가 메모리 참조를 수행해야 한다.   
그것은 많은 작업입니다! 추가 메모리 참조는 비용이 들며, 이 경우 프로세스가 두 배 이상 느려질 수 있다  
  
그리고 이제 해결해야 할 두 가지 실제 문제가 있다.  
  
하드웨어와 소프트웨어를 모두 신중하게 설계하지 않으면 페이지 테이블은 시스템 속도를 너무 느리게 만들뿐만 아니라 너무 많은 메모리를 차지한다. 메모리 가상화 요구에 대한 겉보기에는 훌륭한 솔루션이지만, 이 두 가지 심각한 문제를 먼저 해결해야 한다.

ASIDE: DATA STRUCTURE - THE PAGE TABLE  
현대 OS의 메모리 관리 서브시스템에서 가장 중요한 데이터 구조 중 하나는 페이지 테이블이다. 일반적으로 페이지 테이블은 가상 주소에서 물리적 주소로의 변환을 저장하여 주소 공간의 각 페이지가 실제로 물리적 메모리 내에 어디에 존재하는지 시스템에 알려준다. 각 주소 공간에는 이러한 변환이 필요하기 때문에 일반적으로 시스템에는 프로세스마다 하나의 페이지 테이블이 있다. 페이지 테이블의 정확한 구조는 하드웨어(구형 시스템)에 의해 결정되거나 OS(최신 시스템)에 의해 보다 유연하게 관리된다.  
  
We compile array.c and run it with the following commands: array.c  
  
```bash  
prompt> gcc -o array array.c -Wall -O  
prompt> . /array  
```  
  
물론 이 코드 스니펫(단순히 배열을 초기화하는 것)에 액세스하는 메모리를 제대로 이해하려면 몇 가지를 더 알아야 한다. 먼저 결과 바이너리를 디어셈블(리눅스에서는 objdump, 맥에서는 otool을 사용)하여 어떤 어셈블리 명령어가 루프에서 배열을 초기화하는지를 알아내야 한다. 결과 어셈블리 코드는 다음과 같다.  
  
  
```assembly  
0x1024 movl $0x0,(%edi,%eax,4) // [edi + eax*4] = 0  
0x1028 incl %eax  
0x102c cmpl $0x03e8,%eax // 0000 0011 1110 1000(2) = 1000(10)  
0x1030 jne 0x1024  
```  
  
이 코드는 x86을 조금만 알면 사실 꽤 이해하기 쉽다. 첫 번째 명령은 값 0($0x0으로 표시)을 배열 위치의 가상 메모리 주소로 이동한다. 이 주소는 %edi에 %eax를 더하고 %eax에 4를 곱하여 계산한다.   
  
따라서 %edi는 배열의 기본 주소를, %eax는 배열 index(i)를 보유하게 된다. 배열은 4바이트 정수의 배열이므로 4를 곱한다.  
  
두 번째 명령은 %eax에 저장된 배열 인덱스를 증가시키고, 세 번째 명령은 해당 레지스터의 내용을 16진수 값인 0x03e8 또는 1000과 비교한다. 비교 결과 두 값이 같지 않으면 네 번째 명령은 루프의 맨 앞부분으로 점프한다.  
  
이 명령어 시퀀스가 어떤 메모리 액세스를 수행하는지(가상 및 물리적 수준에서) 이해하기 위해서는 가상 메모리에서 코드 스니펫과 배열이 어디에 있는지, 그리고 페이지 테이블의 내용과 위치를 알아야 한다.  
  
이 예제에서는 64KB(비현실적으로 작은) 크기의 가상 주소 공간을 가정한다. 또한, 1KB의 페이지 크기를 가정하고 있다  
  
여기서 알아야 할 것은 페이지 테이블의 내용과 물리적 메모리 내 위치입니다.   
  
  
선형(배열 기반) 페이지 테이블이 있고, 그것이 물리적 주소 1KB(1024)에 있다고 가정해 봅시다.   
  
이 예제를 위해 매핑한 가상 페이지의 내용은 몇 가지 걱정해야 할 부분이 있다. 먼저 코드가 존재하는 가상 페이지가 있다 페이지 크기는 1KB이므로 가상 주소 1024는 가상 주소 공간의 두 번째 페이지에 있습니다(VPN = 1, 첫 번째 페이지는 VPN = 1). 이 가상 페이지가 물리적 프레임 4(VPN 1→PFN 4)에 매핑되어 있다고 가정해보자.  
  
다음으로 배열 자체가 있다.  
  
  
그 크기는 4000바이트(1000개의 정수)이며, 가상 주소 40000~44000(마지막 바이트는 포함하지 않음)에 존재한다고 가정한다. 이 소수점 범위의 가상 페이지는 VPN = 39 .... VPN = 42입니다. 따라서 이들 페이지의 매핑이 필요한다. 예를 들어 (VPN 39→PFN 7), (VPN 40→PFN 8), (VPN 41→PFN 9), (VPN 42→PFN 10)의 가상-물리 매핑을 가정해 봅시다.  
  
이제 프로그램의 메모리 참조를 추적할 준비가 되었다 실행되면 각 명령어 가져오기는 두 개의 메모리 참조를 생성하는데, 하나는 페이지 테이블에 명령어가 있는 물리적 프레임을 찾기 위한 것이고, 다른 하나는 처리를 위해 CPU로 가져오는 명령어이다. 또한 하나의 명시적 메모리 참조가 mov 명령어 형태로 존재한다. 이것은 먼저 다른 페이지 테이블 액세스를 추가하고(배열의 가상 주소를 올바른 물리적 주소로 변환), 그 다음 배열 액세스 자체를 추가한다.

## 요약  
우리는 메모리 가상화 문제에 대한 해결책으로 페이징이라는 개념을 도입했다.  
페이징은 이전 접근 방식(세그멘테이션 등)에 비해 많은 장점이 있다   
  
첫째, 페이징(설계에 따라)은 메모리를 고정된 크기의 단위로 분할하기 때문에 외부의 파편화로 이어지지 않는다. 둘째, 가상 주소 공간의 미사용 부분을 사용할 수도 있고 사용하지 않을 수도 있는 매우 유연한 방식이다.  
그러나 페이징 지원을 신경 쓰지 않고 구현하면 머신이 느려지고(페이지 테이블에 액세스하기 위해 추가 메모리 액세스가 증가), 메모리가 낭비됩니다(유용한 애플리케이션 데이터가 아닌 페이지 테이블로 메모리가 가득 차게 됩니다).   
  
  
우리는 페이징 시스템을 생각해내는 것이 조금 어렵다고 생각할 것이다. 다행히도 다음 두 장에서는 머신을 더 빠르게 만드는 방법, 메모리 낭비를 없애는 방법을 알려줄 것이다.
